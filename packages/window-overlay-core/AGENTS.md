# AGENTS.md - window-overlay-core

## Authority and Scope

This guide applies to `@narada-core/window-overlay-core`. Read the repository guide at
[`../../AGENTS.md`](../../AGENTS.md) first; this file adds package-specific rules and does not
replace repository doctrine.

This is a private, Windows-only package. It provides reusable WPF overlay mechanics for Narada
operator surfaces. The package requires Node.js >=22 and a PowerShell/WPF-capable Windows desktop
for live operation.

The package's source of truth is under `src/`. The `dist/` directory is generated by the
authoritative TypeScript build and must not be hand-edited.

## Ownership

This package owns the generic overlay contract and mechanics:

- versioned overlay documents, row/action validation, and semantic presentation data;
- one host process per stable overlay id;
- user-local lifecycle and state paths;
- WPF window creation and behavior: visibility, topmost behavior, positioning, opacity, pinning,
  drag persistence, rendering, and controlled actions;
- lifecycle operations: start, inspect, refresh request, explicit focus request, and stop;
- PowerShell host scripts exported through this package;
- bounded diagnostics for lifecycle failures.

The public TypeScript entry point is `src/index.ts`. The generic executable is
`narada-window-overlay-core`.

The public API groups are:

- document: `createOverlayDocument`;
- environment and paths: `normalizeOverlayEnvironment`, `defaultLocalAppDataRoot`,
  `defaultOverlayStateRoot`, `overlayStateDirectory`, and `overlayPaths`;
- observation: `overlayStatus`, `readOverlayDocument`, and `overlayHostScriptPath`;
- lifecycle: `startOverlay`, `requestOverlayRefresh`, `requestOverlayFocus`, `stopOverlay`,
  `inspectOverlay`, and `removeOverlayState`.

Do not put these concerns here:

- provider, quota, mailbox, or Site logic;
- Operator Console authority, router lifecycle, or console-specific document semantics;
- arbitrary command execution;
- browser UI or operator-surface-specific policy.

For Operator Console changes, start at `packages/operator-console-overlay` and
`packages/layers/cli`. Do not edit another package merely because its name contains
`overlay`; establish the owning package first.

## Lifecycle and Durable State

Each overlay id has a user-local state directory. The default root is
`%LOCALAPPDATA%/Narada/window-surface-overlays`. Tests and isolated runs must pass an explicit
temporary `stateRoot` or set `NARADA_WINDOW_SURFACE_OVERLAY_STATE_ROOT`; never use the real
user-local root for tests.

The state files are:

- `document.json`: the latest validated versioned document;
- `overlay.pid`: the host process id used for lifecycle inspection;
- `preferences.json`: persisted position, opacity, pin, and related window preferences;
- `refresh.signal`: an asynchronous request for the running host to re-read its document;
- `focus.signal`: an asynchronous request for the running host to activate its window;
- `restart.command.json`: the fixed restart command supplied by the owning specialization;
- `action-state.json`: durable state for the typed restart action.

Lifecycle semantics:

1. `startOverlay()` validates and writes the document, then starts the host or updates an
   already-running overlay. Starting and idempotent starting must not request foreground activation.
2. `requestOverlayRefresh()` writes `refresh.signal`. It is a request, not proof that rendering
   has completed, and must not request foreground activation.
3. `requestOverlayFocus()` first requires a live overlay, removes a stale signal when refusing,
   then writes `focus.signal`. It returns `focus_requested`; it does not synchronously prove
   that Windows made the overlay foreground.
4. `stopOverlay()` stops the owned host and removes its PID marker and focus signal. It should
   preserve the durable document, refresh marker, and user preference state unless the caller
   explicitly removes state.
5. `inspectOverlay()` reports the durable document, lifecycle state, and action state. It may
   reconcile an abandoned running action to `interrupted`, so it is observational with bounded
   repair rather than a strictly read-only operation.

The host consumes refresh and focus signals asynchronously. A signal is not a second lifecycle
authority. Do not add a new signal file when an existing lifecycle operation or typed action
expresses the intent.

## Focus Contract

Programmatic lifecycle operations preserve the current foreground window. The contract is about
the Windows foreground HWND; it does not guarantee the focused control, caret position, browser
element, or keyboard state inside that window.

User interaction with an overlay may naturally make that overlay foreground. That is different
from a launcher or refresh operation stealing focus.

Use explicit focus only through:

- TypeScript: `requestOverlayFocus(id, options)`;
- generic CLI:
  `pnpm exec narada-window-overlay-core focus --id <id> --state-root <temporary-root>`;
- Operator Console CLI: `narada console overlay-focus`.

A focus request against a stopped or unknown overlay must fail clearly and leave no stale focus
signal. The host's OS-level foreground activation remains subject to Windows desktop policy.

## Document and Action Safety

- Overlay ids must remain stable and satisfy the package validation contract.
- Row and action URLs may use only `http:` or `https:`.
- Restart is a typed action whose executable command is fixed by the owning specialization.
- Never accept executable targets or arbitrary commands from a document.
- Keep document schema and result schema versioned.
- When changing state-file names, schemas, or persisted preferences, preserve compatibility or add
  an explicit migration and tests.
- Keep secrets and provider data outside overlay documents and durable presentation state.

## Source, Build, and Export Rules

Authoritative sources include:

- `src/index.ts`, the public TypeScript API source;
- `src/index.d.ts`, a checked-in compatibility declaration that must stay aligned with the source;
- `src/cli.ts`;
- `src/window-surface-overlay.ps1`;
- `src/Start-WindowSurfaceOverlay.ps1`;
- `src/Stop-WindowSurfaceOverlay.ps1`;
- `src/Inspect-WindowSurfaceOverlay.ps1`;
- `src/Install-WindowSurfaceOverlay.ps1`.

Keep `src/index.d.ts` aligned with exported TypeScript APIs. The package resolves its public
declarations from generated `dist/index.d.ts`; run the build to regenerate `dist/index.js` and
generated declarations. Do not patch generated output by hand.

The package uses ESM, TypeScript with `tsc`, and the package scripts in `package.json`.
Use the repository's package manager and do not introduce a second build system.

## Verification Tiers

Run the package-local checks for any source change:

- `pnpm --filter @narada-core/window-overlay-core test`;
- `pnpm --filter @narada-core/window-overlay-core typecheck`;
- `pnpm --filter @narada-core/window-overlay-core build`.

Run the Windows live check when changing PowerShell/WPF behavior, lifecycle, visibility, refresh,
positioning, or focus:

- `pnpm --filter @narada-core/window-overlay-core test:live`.

The live test requires an interactive Windows desktop, creates temporary WPF windows, may change
the foreground window during its explicit-focus case, and must clean up all hosts and temporary
state. A skipped live test on a non-Windows machine is not evidence of desktop correctness.

Run integration checks when changing the public API, Operator Console specialization, or Narada CLI
wiring:

- `pnpm --filter @narada-core/operator-console-overlay test`;
- `pnpm --filter @narada-core/operator-console-overlay typecheck`;
- `pnpm --filter @narada-core/operator-console-overlay build`;
- `pnpm --filter @narada-core/cli typecheck`;
- `pnpm --filter @narada-core/cli build`.

After edits, run `git diff --check`. Keep unrelated worktree changes untouched and do not commit
generated output unless the repository explicitly tracks it.

## Change Checklist

Before finishing a change, confirm:

- the owning package is correct;
- the foreground-window contract is preserved;
- asynchronous signals are not mistaken for completed operations;
- tests use isolated state roots;
- the relevant verification tier was run;
- declarations, README guidance, and CLI help remain aligned with the implementation.
